# 序界（LiveBlocks）架构基线

> 状态：基线草案。本文件只定义链路、模块边界与待决事项，不含实现。
> 目标形态：桌面实体卡片 → 摄像头识别 → 排列还原 → 语法解析（AST / JSON）→ 模拟或硬件执行 → 反馈显示。

## 1. 端到端链路

```
S1 采集          摄像头帧 / 合成帧
S2 卡片识别      ArUco 候选 → 卡片候选（id + 角点 + 位姿 + 置信度）
S3 排列还原      卡片候选 → 排列（有序位置、朝向、分组、冲突处理）
S4 语法解析      排列 → AST（语法树，带错误定位）
S5 规范化        AST → IR（JSON，稳定、可序列化、可回归比对）
S6 执行           IR → 指令序列 → 模拟器 或 硬件驱动
S7 反馈与调试    执行状态/结果 → 调试界面叠加、模拟显示、硬件显示/LED
```

每一层都有显式的数据契约（见 `docs/PROTOCOL.md`，草案），层间只通过契约交互，不允许跨层读取内部状态。这样 S1–S7 可以分别被替身实现（合成帧、录制的检测结果、固定 IR）驱动测试。

### 1.1 数据流（一次完整闭环）

1. `S1` 取一帧（或一组合成帧），做畸变校正与版面归一化，输出带时间戳的帧对象。
2. `S2` 在帧内检测 ArUco 标记，得到标记候选；再按「标记 = 卡片」的映射规则组装成**卡片候选**。此阶段不确定卡片语义，只报「这是什么卡、在哪、朝哪、多可信」。
3. `S3` 把所有候选按几何关系还原成**排列**：行/列分簇、按阅读方向排序、判定朝向、丢弃低置信度或重复候选、报告歧义。
4. `S4` 按排列内容做语法分析，得到 **AST**；语法错误必须带卡片级定位（哪张卡、哪个位置、期望什么）。
5. `S5` 把 AST 规范化为 **IR JSON**：解析引用、展开默认值、稳定键序，便于快照测试与跨语言消费。
6. `S6` 执行器按 IR 逐条执行，产出**指令事件流**与执行结果；模拟器与硬件后端实现同一接口，硬件后端未就绪时以模拟器为准。
7. `S7` 调试界面把 S1–S7 的中间产物与耗时同时呈现；同一次运行的中间产物可落盘为「运行记录」，用于回归与人工测试的证据。

## 2. 模块边界

| 模块 | 职责 | 输入 | 输出 | 明确不做 |
| --- | --- | --- | --- | --- |
| `capture`（S1） | 取帧、校正、归一化、时间戳 | 摄像头设备 / 合成帧源 / 录制文件 | `Frame` | 不做识别、不做业务判定 |
| `vision.detector`（S2a） | ArUco 检测与位姿估计 | `Frame` | `MarkerCandidate[]` | 不解释卡片语义，不做排列 |
| `vision.card`（S2b） | 标记 → 卡片候选组装、卡片字典查询、置信度聚合 | `MarkerCandidate[]` + 卡片字典 | `CardCandidate[]` | 不做排序、不做语法 |
| `layout`（S3） | 分簇、排序、朝向、去重、歧义标记 | `CardCandidate[]` | `Layout` | 不解释语法、不执行 |
| `parser`（S4） | 词法/语法分析、错误定位、AST 构造 | `Layout` + 文法定义 | `Ast` + `Diagnostic[]` | 不做执行、不做 I/O |
| `ir`（S5） | AST → 规范化 IR，schema 校验，键序稳定化 | `Ast` | `Ir`（JSON） | 不执行、不含环境副作用 |
| `runtime`（S6） | 指令调度、状态机、变量/栈、超时与撤销 | `Ir` | `ExecEvent[]` + `ExecResult` | 不含具体设备协议 |
| `backend.sim`（S6） | 纯软件执行，虚拟时钟，确定性 | IR 指令 | 事件流 | 不碰硬件 |
| `backend.hw`（S6） | 硬件驱动适配（串口/网络），设备抽象 | IR 指令 | 事件流 | 不做语法，不做识别 |
| `feedback`（S7a） | 把事件流映射为显示/灯光/声音反馈 | `ExecEvent[]` | 反馈指令 / 渲染状态 | 不做执行逻辑判断 |
| `ui.debug`（S7b） | 分层可视化、单步、回放、耗时与置信度展示 | 各层产物 + 运行记录 | 人可读界面 | 不修改业务数据 |
| `synth`（`fixtures` 的生成器，LB-002） | 合成卡片图像生成、黄金样例与快照基准 | 卡片字典、版式定义、随机种子 | 图像（PNG）+ 真值 JSON | 不做识别、不参与运行时逻辑 |

**边界约束**

- 只有 `vision.*` 能产出「卡在哪里」，只有 `layout` 能决定「卡的先后」，只有 `parser` 能产出 AST，只有 `runtime` 能产生执行事件。
- `ir` 是唯一的跨语言/落盘边界：模拟执行、硬件执行、调试界面、回归测试都只消费 IR 与事件流。
- 硬件相关能力统一藏在 `backend.hw` 之后，上层不得出现具体引脚、波特率、设备路径。

## 3. 关键设计要点

### 3.1 卡片图像与识别

- 每张实体卡片至少带一个 ArUco 标记，标记承载「卡片身份」，卡片朝向可视需要由标记的单应性推出。
- 识别输出候选而非结论：多帧合并、多候选并列、置信度不足时保留候选并标注，交由 `layout` 决定是否采用。
- 需要区分「检测到标记」与「这是一张有效卡片」：标记在字典中但未登记、被遮挡、被裁切的情况要单独归类，不能静默丢弃。

### 3.1a 合成卡片生成器（LB-002 落地）

`src/liveblocks/synth/` 是 §2 表格里 `synth` 那一行的实现，只负责「造图 + 出真值」：

- 输入是**数据文件**：卡片字典（`card_id → marker_id + card_face`）、ArUco 位表、卡面版式
  （尺寸、标记位置、静区、标签）与场景预设（相机内参、每卡位姿、遮挡物、光照、位姿抖动）。
- 输出是灰度 PNG + 真值 JSON（卡片 id、标记 id、`pose`、卡片与标记的四个角点、可见比例、
  `status`），角点顺序与 `docs/PROTOCOL.md` §3.1 一致。
- 渲染不依赖任何第三方库（自带 PNG 编码、位表与点阵字体），随机量全部来自一个种子，因此
  「同一个种子 → 同样的字节」。设计与取舍见 `docs/DECISIONS.md` D-012。
- 它**不做识别**，也不评估识别效果；真值只是给 LB-003 之后各层做基准。

### 3.2 排列（ArUco 候选 → 排列）

- 排列还原是纯几何 + 规则问题：先按位姿分簇，再在簇内按阅读方向（可配置，默认左上→右下）排序，处理旋转卡片的朝向归一化。
- 必须显式处理歧义：并排间隙模糊、两行被误判为一行、镜像卡片、同一张卡被重复检测。
- 排列结论需要携带「为什么这样排」的最小依据（候选 id、位置、使用的排序规则），供调试界面展示。

### 3.2a 排列层（LB-004 落地）

`src/liveblocks/layout/` 是 §2 表格里 `layout` 那一行的实现：

- 输入是 §3.2 的 `CardCandidateList`（只用 `candidate_id` / `card_face` / `orientation_quadrant` /
  `center_px` / `confidence` / `status`），输出是 §4 的 `Layout`；**不解析语法**（LB-005）。
- 五步固定顺序：过滤身份未知的候选（`LB-L003`）→ 去重（`LB-L002`）→ 沿阅读方向的换行轴间隙分簇
  → 行内按阅读方向排序 → 朝向归一 + 间距/行分组歧义诊断（`LB-L001` / `LB-L004` / `LB-L005`）。
- 阈值都是「典型卡距」的倍数，卡距由候选位置自适应估计（候选里没有物理尺寸），可用 `--pitch-px`
  覆盖。`Layout.basis` 记录卡距、阈值与每行的候选 id，供调试界面与回归使用。
- 设计与协议缺口见 `docs/DECISIONS.md` D-015。

### 3.3 AST 与 JSON

- 解析结果是 AST 而非直接执行计划；AST 保留来源位置（卡片 id / 排列下标），使错误能指回实体卡片。
- IR 是 AST 的规范化投影：确定性输出（稳定键序、无浮点抖动、无时间戳），便于快照回归与人工审阅。
- 文法与 IR schema 都是**草案**，改动需在 `docs/DECISIONS.md` 记一条并说明兼容性。

### 3.3a 规范化 IR（LB-006 落地）

`src/liveblocks/ir/` 是 §2 表格里 `ir`（S5）那一行的实现：

- 输入是 §5 的 `Ast`，输出是 §6 的 `Ir`；一条 `Command` 折成一步 `step`（`op` 取卡面、`args` 折成
  「一个数值参数 + `unit`」、`source` 写 `{row, slot}`、`step_id` 密集编号）。
- `op` 表（卡面 → op / 参数 / 元数 / 单位）与 `limits` 缺省值写在 `src/liveblocks/ir/ops.py`，
  人类可读的同一份在 `docs/IR.md`；schema 是入库的 `src/liveblocks/data/ir_schema.json`，
  配一个零依赖的最小校验器 + 语义校验（`validate_ir`）。
- 确定性靠「固定构造顺序 + 单一序列化入口 + 只有整数 + 无时间戳」保证；golden 快照与「两次规范化
  字节一致」都有测试。问题语句报 `LB-I0xx` 且**不进 IR**（不做截断/补零）。**不执行**（LB-007）。
- 设计与协议缺口见 `docs/DECISIONS.md` D-017。

### 3.4 执行

- 一次执行是「IR + 环境」→「事件流」的纯函数式过程（模拟后端）；硬件后端允许真实副作用，但事件流格式一致。
- 必须有超时、步数上限与中断，避免卡片排列导致死循环。
- 未就绪的硬件能力用模拟后端顶替，并在事件中标记 `backend: "sim"`，避免把模拟结果当成硬件验证。

### 3.5 调试界面

- 分栏展示：原帧 + 叠加（检测框、标记 id、置信度）→ 排列结果 → AST → IR → 事件流 + 耗时。
- 支持从运行记录回放与单步，便于问题复现；界面本身不改数据，只读。
- 首阶段界面只服务于开发者，不对真实用户展示。
