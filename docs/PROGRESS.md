## 4. 已知限制与阻塞

- **软件闭环（P0）已经跑通并被回归守住，但还没有接硬件**：一条命令 `liveblocks e2e run` 真跑「生成 → 识别 → 排列 → 解析 → IR → 模拟」六阶段并落盘 §8 运行记录，`liveblocks e2e regression` 用记录形状 + 指纹式黄金基准 + 破坏注入自检 + 固定时间上界把它守住；`Ir` 到现在只被**模拟后端**跑过，**没有任何硬件后端**（LB-013），也没有任何真实摄像头 / 实体卡片的证据。
- **LB-009 已知限制（详见 `docs/DECISIONS.md` D-020 与 `docs/E2E.md`）**：
  1. **记录不入库**：`runs/e2e` 在 `.gitignore` 里——`RunHeader.timings_ms` 是记录时实测的墙钟耗时，每跑一次都不一样；入库的是**黄金基准**（每层文档的指纹、`kind` 序列、行数、计数）与记录形状的约定；
  2. **只跑合成图**：`backend` 恒为 `sim`，生成层是 LB-002 的合成卡片图（6 个入库场景），不接真实摄像头、不做标定；模拟通过 ≠ 硬件验证；
  3. **时间上界不是性能基线**：60 s / 20 s 只保证「别挂死」；实测值（整份约 9–11 s，瓶颈是生成层的纯 Python 光栅化）只作证据，不进基准；
  4. **`--corrupt` 是自检开关**：注入方式确定（抹平生成图 / 删该层一个必填字段），不支持按场景分别注入；`--no-self-check` 会让「破坏时回归会失败并点名到层」这条验收显示未通过（退出码 1），这是刻意的；
  5. **失败定位取「最早一层」**：破坏发生在哪层，下游都是后果，所以只点名最上游的一层；如果同一次破坏在多处出现（例如手改基准 + 上游层变更），摘要仍只给最早那层，其余逐条列在后面。

  1. **合成管线 ≠ 实体卡**：`cardsheet verify` 只是把渲染出来的像素当成一帧再识别（无镜头畸变、无运动

  2. **分辨率与识别窗口耦合**：默认 4 px/mm 是为 LB-003 的 21 px 自适应窗口选的。实测 6 px/mm（模块
     24 px）时默认窗口会把整块黑模块当成本地背景而**读不出标记**，要 `--block 31` 才读得出，但那时卡面
     文字会冒出上百个「形状对、身份未定」的候选；这是实现耦合，不是打印质量结论；
  3. **只对「16 张卡 / 一页」出过证据**：多页排版的代码路径有单测，没有出样；
  4. **点阵字形只有 ASCII**：卡面标签与页眉页脚只能是 ASCII，中文卡片名（`label`）不进像素；
  5. **PDF 只是一个整页图像**：不可搜索、无矢量文字，放大到高倍数会看到像素；裁切线是灰线而不是矢量
     裁切标记（Marks）；
  6. **卡面静区小于静区规则**（2.5 mm vs 4 mm）是版式定义带来的既成事实，本单只如实报告与测试，不改版式
     （改版式要重生成 LB-002 fixtures，属另一单）；
  7. **没有卡面美术结论**：颜色、图案、正反面印刷都在本单之外。
- **LB-032 未改动 ROADMAP**：`docs/ROADMAP.md` 的范围与优先级一个字节都没改，对上游代码（`synth/`、
  `vision/`）也是一行未改——`sheet` 包只调用它们（`render_card_texture` / `recognize`）。
- **LB-030 已知限制（详见 `docs/DECISIONS.md` D-021 与 `docs/CAPTURE.md` §8）**：
  1. **只吃 8bit 灰度**：页面在浏览器里做灰度转换（`0.299R + 0.587G + 0.114B`），PNG 请求体只接受
     8bit 灰度 PNG；彩色/16bit PNG 直接 `LB-C003` 拒绝（不静默降级）。扩展 `decode_gray` 会动 LB-002
     的「字节可复现」契约，不在本单范围；
  2. **实拍真值不是测量**：`status` 缺省 `ok` 且标 `status_assumed`，`center_px` 由「标记四边形 +
     卡面版式」外推（`center_source`），四角拿不到的卡不进 `scene.json`——所以实拍样本的「卡片中心误差」
     只说明几何自洽，**不能当识别精度**引用；
  3. **没有标定**：`Frame.intrinsics` 不填（LB-031 的范围），实拍样本的 §3 输出里没有位姿；
  4. **帧令牌是内存态**：只留最近 16 帧，进程重启即失效（`LB-C007`），落盘产物不受影响；
  5. **不做公网鉴权**：默认只绑 `127.0.0.1`；`--host 0.0.0.0` 的局域网暴露与手机 `getUserMedia`
     所需的 HTTPS 都留给运维侧隧道（「不做」的一条），代理未做也未验证这条链路；
  6. **页面一次只标一张卡**：API 的 `annotations[]` 支持多条（multi-row 6 卡在测试里这样跑通），
     但页面表单只填一条；不支持采完改判（重采，或在 `capture.json` 里如实记一笔后重采）；
  7. **叠加图只画识别层**：不画排列槽位（要五层视图用 `liveblocks ui view`）。
- **LB-030 顺带发现的 LB-003 统计缺陷（未修，只报告）**：`vision.stats._evaluate_result` 的「误检（extra）」
  在结构上恒为 0——`identified_markers` 只在遍历真值卡片时填充，因此「真值里不存在的 marker」永远进不了
  这个列表。改了会动 LB-003 的报表口径与既有测试，属另一单；在此之前**不得**把「误检 0」当作识别可靠的证据
  （LB-030 的 refused 样本只用「识别数 + 漏检 + 状态」说明问题）。
- **LB-030 未改动 `docs/PROTOCOL.md` 与 `docs/ROADMAP.md`**：协议只报告缺口（`docs/CAPTURE.md` §9），
  ROADMAP 的范围与优先级一个字节都没改。对上游代码的唯一改动是 `vision/stats.py` 的 `SCENE_KINDS`
  （加法式：多认一个 `LiveCaptureScene`，合成场景行为不变）。
- **本单不派发后续工单**：ROADMAP 条目只是 backlog，开新 Issue 需仓库所有者确认（`AGENTS.md` §5）。

## 5. 更新规则

1. 每个合并的 PR 更新本文件对应行，并写清证据位置（命令、文件、Issue 链接；CI 结果等 CI 真跑完再补）。
2. 证据失效（版本已变）时把该行退回「计划中」，不保留过期「已验证」。
3. 「待硬件验证」只在人工测试 Issue 有结论且仓库所有者确认后迁移。
