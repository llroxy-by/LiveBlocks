# 序界（LiveBlocks）路线图 — 基线

> 状态：基线草案。本文件是 **Backlog**，不是排期承诺。
> 每一条都可以**独立开一个 Issue**：范围自洽、依赖明确、验收条件可观察。优先级 P0 > P1 > P2，同一优先级内按依赖先后排列。

## 0. 排序原则

1. 先让「纯软件闭环」跑通并**可回归**，再接硬件。
2. 顺序固定为：**软件 MVP 骨架与测试 → 虚拟卡片生成 → 识别 → 解析 → 模拟执行 → 调试界面** → 之后才是固件、实体卡片、真实联调与交付。
3. 一个任务只做一层，跨层任务要拆开；验收条件必须能用命令输出或可见界面判断，不写「效果良好」这类主观标准。
4. 任何需要硬件实测的结论，只写在 HARDWARE / PROGRESS 的「待硬件验证」，不进 P0 的完成定义。

## 1. 依赖总览

```
LB-001 骨架与测试
   └─ LB-002 虚拟卡片生成
        └─ LB-003 识别（ArUco 候选）
             └─ LB-004 排列还原
                  └─ LB-005 语法解析（AST）
                       └─ LB-006 规范化 IR
                            └─ LB-007 模拟执行
                                 └─ LB-008 调试界面
                                      └─ LB-009 端到端回归与运行记录

LB-003 → LB-010 标定与畸变校正（可与 LB-004 并行）
LB-010 → LB-020 真实摄像头接入
LB-011 固件骨架 ─┐
LB-012 实体卡片制作 ─┤
LB-013 硬件后端（backend.hw） ← LB-011
LB-020 真实闭环联调 ← LB-007, LB-010, LB-012, LB-013
LB-021 交付与打包 ← LB-020
```

## 2. 第一批：软件 MVP 骨架与测试（P0）

### LB-001 仓库工程骨架与测试框架
- **范围**：目录结构（`src/`、`tests/`、`fixtures/`、脚本）、依赖声明、一个能跑通的最小测试与本地检查脚本、CI 或本地等价检查。
- **依赖**：无（本单只出文档，代码从裸仓库开始）。
- **可观察验收**：`README` 中的命令可原样执行；一条命令能跑全量测试且输出用例数 ≥1；故意让断言失败时命令以非零码退出；CI（若启用）对 PR 显示出检查结果。
- **不做**：不实现任何业务模块。

### LB-002 合成卡片图像生成器（虚拟卡片）
- **范围**：按卡片字典与版式定义生成 ArUco 卡片图像（单卡、多卡、任意角度/间距/光照噪声/遮挡/裁切），输出图像 + 真值 JSON。
- **依赖**：LB-001。
- **可观察验收**：给定固定随机种子，生成结果字节可复现；每张图附真值（卡片 id、角点、位姿）；至少覆盖「正常、轻微旋转、重叠、裁切、低光照」5 类样例，样例作为 fixtures 入库。
- **不做**：不做识别，不评估识别效果。

### LB-003 识别模块（ArUco 候选 → 卡片候选）
- **范围**：标记检测 + 卡片字典映射 → `CardCandidateList`（含 `status`、置信度、朝向）。
- **依赖**：LB-002。
- **可观察验收**：对 LB-002 的 fixtures 跑识别，输出符合 `docs/PROTOCOL.md` §3 的 JSON；「正常」样例无漏检，「裁切」样例标 `clipped`，未登记标记标 `unknown_card`；有一份可读的准确率/漏检统计输出。
- **不做**：不排序、不解析、不执行。

### LB-004 排列还原（卡片候选 → Layout）
- **范围**：分簇、阅读方向排序、朝向归一、去重、歧义诊断。
- **依赖**：LB-003。
- **可观察验收**：给定 fixtures 的卡片候选，输出 `Layout`（§4）；两行样例被正确分成两行；间距歧义样例产出 `LB-L001`；重复候选去重后有 `LB-L002`；所有排序结论可追溯到候选 id。
- **不做**：不解析语法。

### LB-005 语法解析（Layout → AST）
- **范围**：最小文法（P0 定为「语句序列 + 字面参数」），错误定位到行/槽位/卡片。
- **依赖**：LB-004。
- **可观察验收**：合法样例得到符合 §5 的 AST；非法样例产出带 `span` 与 `origin` 的 `LB-P0xx` 诊断且不崩溃；文法定义有独立文档或注释并可被测试引用。
- **不做**：不做求值、不做执行。

### LB-006 规范化 IR（AST → Ir）
- **范围**：AST → 确定性 IR，schema 校验，缺省值填充，`limits` 显式化。
- **依赖**：LB-005。
- **可观察验收**：同一 AST 规范化两次输出字节一致；未知 `op` 报 `LB-I001`；IR 通过 schema 校验；golden 文件快照测试通过。
- **不做**：不执行。

### LB-007 模拟执行器
- **范围**：IR → `ExecEvent[]` + `ExecResult`，虚拟时钟，步数/超时限制，中断。
- **依赖**：LB-006。
- **可观察验收**：样例 IR 执行后事件 `seq` 严格递增且 `backend:"sim"`；死循环样例以 `limit_exceeded`/`timeout` 结束而非挂死；测试总耗时在设定上限内；带一个可读的状态输出（如最终状态 JSON）。
- **不做**：不接硬件，不做界面。

### LB-008 调试界面（分层可视化）
- **范围**：一屏展示帧叠加、排列、AST、IR、事件流与分层耗时；支持从运行记录回放与单步。
- **依赖**：LB-003、LB-004、LB-005、LB-006、LB-007。
- **可观察验收**：打开样例运行记录可看到五层数据同时呈现；回放同一记录两次结果一致；界面对缺失/损坏字段给出可见提示而非崩溃；附截图作为证据。
- **不做**：不做产品级 UI，不对最终用户发布。

### LB-009 端到端回归与运行记录
- **范围**：一条命令跑「生成 → 识别 → 排列 → 解析 → IR → 模拟」全链路；JSONL 运行记录落盘（§8）；黄金样例基准与失败摘要。
- **依赖**：LB-002 … LB-008。
- **可观察验收**：全链路命令退出码 0；运行记录包含全部层的 `kind` 且有 `RunHeader`；人为破坏一个 fixture 时回归明确失败并指出层级；回归在固定时间内完成。
- **不做**：不接真实摄像头。

## 3. 第二批：硬件与真实环境（P1）

> 本批拆成两半：**LB-030 ~ LB-034 不依赖实物**，可以用合成数据、虚拟串口、可打印模板和人手里的任意摄像头完成，先做；**LB-010 / LB-011 / LB-012 / LB-013 / LB-020 的实做与实测部分**要等硬件到位与人实测，不得在无证据时开工或声明通过。
>
> 摄像头不锁型号：手机、笔记本内置、USB UVC 一律走同一采集路径（浏览器 `getUserMedia`）。板子已知为 ESP32-C3 SuperMini。
> 共同红线：任何一条都**不得**在无实测的情况下往 `docs/PROGRESS.md` 的「已验证」写结论；依赖实物的那部分必须留「待硬件验证」。

### LB-030 Web 摄像头采集与人工辅助测试台
- **范围**：一条命令起本地服务（优先零新增依赖），页面用浏览器 `getUserMedia` 选择任意摄像头（手机前置/后置、笔记本内置、USB），支持单帧抓拍与连续取帧；`POST /api/frame` 返回 §3 `CardCandidateList` 与识别叠加图；`POST /api/capture` 把当前帧与人工标注（卡片 id、角色、可选角点）落成 `fixtures/live/<时间戳>/`；`GET /api/captures` 列已采样本；页面能标「这帧识别错了」并把失败样本单独归档。
- **依赖**：LB-003；LB-004 可选（叠加排列结果）。
- **可观察验收**：① 离线：`pytest tests/test_serve_cam.py` 用 TestClient 上传 `fixtures/scenes/*.png`，返回的 §3 JSON 与 `recognize detect` 命令行逐字段一致，叠加图 PNG 可解码且尺寸与输入一致；② 离线：采集目录能被 `recognize report` 直接消费；③ 离线：页面无外网 CDN 依赖，断网可加载（相机权限除外）；④ 人工：在手机上打开链接、选后置摄像头、对着一张卡能看到叠加框与卡片 id —— 这条由人在 Web 上验，agent 不得代填。
- **不做**：不做视频录制与上传、不做多用户与账号、不做公网鉴权（由运维侧隧道加 token 负责）、不改 `PROTOCOL.md`。

### LB-031 标定算法与标定文件格式（LB-010 算法侧）
- **范围**：棋盘格与 ChArUco 标定流程；标定文件 JSON 格式（内参、畸变、重投影误差、图像尺寸、标定图数量、时间戳）；`Frame.intrinsics/distortion` 的填充路径；给合成器加**镜头畸变模型**（径向 + 切向），按给定真值内参生成带畸变的场景，作为可复现的回归数据。
- **依赖**：LB-003；LB-030 可选（真实帧来源）。
- **可观察验收**：对合成畸变场景（内参真值已知）跑标定，打印重投影误差且低于设定阈值；校正前后同一静态场景的角点重复性给出均值与最大值（像素）对比；`liveblocks calibrate report` 一条命令复现上述全部数字，退出码 0。真实摄像头的标定数字**不在本单验收内**。
- **不做**：不冻结摄像头型号；不声明任何真实设备的重投影误差或可用距离。

### LB-032 实体卡片规范草案与标记模板生成器
- **范围**：卡片尺寸、标记尺寸、静区、基材、打印工艺、批次编号与质检项的规范草案（`docs/CARD-SPEC.md`）；`liveblocks cardsheet` 生成可打印的标记页（A4 排版，含裁剪线、静区、卡片编号、朝向标记），输出 PNG 或 PDF；附一个手绘降级版说明（黑白格加编号，供没打印机时用）。
- **依赖**：LB-002 的卡片字典与 ArUco 位表；LB-003 识别。
- **可观察验收**：生成的标记页经合成管线（把页面渲染成图再识别）能正确读出全部 id 与朝向；规范文档里每个数字都能追到字典或静区规则，凡无实测依据的项必须显式标「待实测」；模板生成是确定性的（同参数两次字节一致）。
- **不做**：不声称任何打印工艺、基材、可识别距离的实测结论；不替用户决定最终卡面美术。

### LB-033 硬件后端协议层与虚拟串口模拟设备（LB-013 协议侧）
- **范围**：`backend.hw` 的事件流映射（与 sim 同为 §7.1 格式，`backend:"hw"`）；串口帧格式（帧头、长度、CRC、序号、命令与事件类型）；传输抽象 `Transport` 并提供 pty 与真实串口两种实现；断连、超时、重连的错误事件模型；一个纯 Python 的**设备模拟器**，用 pty 假装设备跑完整协议。
- **依赖**：LB-007。串口帧格式由本单定义，供 LB-011 固件与 LB-034 使用，不要求 LB-011 先完成。
- **可观察验收**：同一份 IR 分别用 sim 与 hw 后端执行，事件流结构与关键状态一致（`tests/test_backend_parity.py`）；pty 模拟器被拔线时产生明确的断连错误事件且不阻塞、可重连；协议层单测覆盖帧解析的截断、CRC 错、序号乱序三类异常。
- **不做**：不做真实硬件联调（属 LB-020）；不支持 ESP32-C3 以外的板子；不声称灯效或屏幕已驱动。

### LB-034 ESP32-C3 SuperMini 固件骨架
- **范围**：最小固件：上电启动日志、串口心跳、命令分发占位、灯效驱动占位；全部引脚来自 `config/board.esp32c3-supermini.json`（默认值标注待实测），代码中零硬编码 GPIO；构建脚本与烧写说明。
- **依赖**：LB-033 的帧格式；硬件已知为 ESP32-C3 SuperMini。
- **可观察验收**：源码能从零编译通过（CI 里只编译、不烧写，编译产物与命令写入 `docs/PROGRESS.md`）；配置 schema 校验通过且源码里搜不到裸 GPIO 数字；心跳帧格式与 LB-033 的模拟器逐字节一致（用模拟器做的协议比对测试）。烧写、串口日志、复位自恢复由人实测。
- **不做**：不做真实烧写与联调；不做 OTA；不做外壳与供电。


### LB-010 摄像头标定与畸变校正
- **范围**：标定流程（棋盘格/ChArUco）、标定文件格式、`Frame.intrinsics/distortion` 填充。
- **依赖**：LB-003（算法侧），设备侧见 HARDWARE §1.1。
- **可观察验收**：标定产出可复现的标定文件与重投影误差数值；校正前后同一静态场景的角点重复性有量化对比。
- **不做**：不冻结硬件选型。

### LB-011 固件骨架
- **范围**：MCU 侧最小固件：启动、串口协议、心跳、灯效/屏驱动占位；引脚全部来自配置文件。
- **依赖**：HARDWARE PN-* 与 PW-* 项确认。
- **可观察验收**：烧写后串口可见启动日志与心跳；拔插复位可自恢复；引脚来自配置而非硬编码。**在硬件确认前不得开工。**

### LB-012 实体卡片制作规范
- **范围**：卡片尺寸、标记尺寸与静区、基材、打印工艺、批次编号与质检项。
- **依赖**：HARDWARE §1.4 实测结论。
- **可观察验收**：一批卡片按规范制作完成，抽样实测被模拟/真实识别链路正确识别并附照片与统计数据。

### LB-013 硬件后端（backend.hw）
- **范围**：`runtime` 指令 → 设备协议，事件流与模拟后端同格式（`backend:"hw"`）。
- **依赖**：LB-007、LB-011。
- **可观察验收**：同一 IR 分别用 sim 与 hw 后端执行，事件流结构一致、关键状态一致；hw 后端断连时有明确错误事件而非阻塞。

### LB-020 真实闭环联调
- **范围**：真实摄像头 + 实体卡片 + 硬件反馈跑通全链路，记录延迟与失败模式。
- **依赖**：LB-007、LB-010、LB-012、LB-013。
- **可观察验收**：按硬件测试模板提交一次完整人工测试，含视频/日志、端到端延迟数据、失败模式清单；`docs/PROGRESS.md` 对应项从「待硬件验证」迁到「已验证」。

## 4. 第三批：交付（P2）

### LB-021 交付与打包
- **范围**：安装/部署说明、外壳与线材清单、快速上手、已知限制、故障排查、版本与回滚方式。
- **依赖**：LB-020。
- **可观察验收**：在一台「干净」机器上仅按文档即可复现最小闭环；文档中每条命令与路径真实存在；附一次从零安装的记录。

## 5. 状态与入口

- 各条目的当前状态（未开始 / 计划中 / 进行中 / 已验证 / 待硬件验证）在 `docs/PROGRESS.md` 维护。
- 人工测试与反馈统一走 GitHub Issues + `.github/ISSUE_TEMPLATE/hardware-test.md`。
- 本路线图不做任务派发；开新 Issue、调整优先级需仓库所有者确认（见 `AGENTS.md` §5）。
