## D-001 首阶段以纯软件闭环为目标

- **背景**：仓库目前只有初始 README；硬件选型、电源、引脚均未验证，直接做硬件会把不确定性混进架构验证。
- **决策**：第一阶段只做纯软件闭环：合成卡片图像 → 识别 → 排列 → 解析 → IR → 模拟执行 → 调试界面。真实摄像头与硬件执行放到后续批次。
- **影响**：所有 P0 任务的验收都不依赖硬件；模拟执行器必须与未来硬件后端共用同一事件流格式。
- **待办**：在 `backend.hw` 实现时补一次「同 IR 双后端一致性」验证（LB-013）。

## D-002 层间契约用 JSON，IR 与事件流为唯一落盘边界

- **背景**：链路有 7 个阶段、多种实现可能（Python/TS/固件），需要可序列化、可回归、可人工审阅的边界。
- **决策**：层与层之间只通过 `docs/PROTOCOL.md` 定义的对象交互；跨语言、落盘、回归一律以 `Ir` / `ExecEvent` / `ExecResult` 为准。
- **影响**：模块可独立替换与独立测试；调试界面与回归测试只消费契约，不读内部状态。
- **待办**：协议冻结前补齐 schema 校验工具与 golden 文件（LB-006、LB-009）。

## D-003 协议文档以草案版本化，只做加法式演进

- **背景**：文法与 IR 都会反复调整，早期若宣称稳定会误导下游。
- **决策**：`docs/PROTOCOL.md` 长期标注「草案 v0.0.x」；只加字段不改语义时提升 `minor`，破坏性变更提升 `major` 并在此文件记录迁移说明。消费者必须容忍未知字段与未知枚举。
- **影响**：早期实现可以并行推进；不足是接口随时可能变动，文档必须同步维护。
- **待办**：每次格式变更在同一 PR 内更新协议版本与 `docs/PROGRESS.md`。

## D-004 实现语言与运行时（提案，未定）

- **背景**：需要选定 MVP 骨架的语言，影响 LB-001 的具体内容。
- **提案**：Python 3.11+ + OpenCV（ArUco 支持完整、原型快），测试用 pytest；调试界面先用本地 Web 前端或轻量 GUI。
- **备选**：TypeScript/Node（前端与界面统一，但 ArUco 生态较弱）。
- **影响**：等待确认期间，LB-001 的验收只写「命令可执行、测试可跑」，不绑定具体命令实现。
- **待办**：由仓库所有者确认后再落地 LB-001 的脚本细节。**未确认前不得擅自锁定语言。**
- **进展（2026-11-23）**：LB-001 骨架已按本提案以 Python 3.11 + pytest 落地，作为**临时**选择记录在 D-011；本条仍为「提案」，语言未锁定。

## D-005 P0 文法取最小集（提案，未定）

- **背景**：文法表达力决定了 AST、IR 与执行器的规模。
- **提案**：P0 只支持「语句序列 + 字面参数」，即卡片按行顺序执行，不引入变量、条件、循环、函数。
- **影响**：解析器与执行器都能在一两个任务内跑通；后续扩展需要提升 `grammar_version`。
- **待办**：与 Q4/Q5 一并确认；若改为立即执行型指令，需重写 D-002 的 IR 语义说明。

## D-006 单并发 + 人工合并

- **背景**：多个代理并行改同一批文件会产生冲突与不可追溯的合并。
- **决策**：同一时间只推进一个实现任务；所有 PR 由人审阅合并，代理不自动合并、不绕过评审、不开 auto-merge。
- **影响**：吞吐受限但历史干净、可回滚。
- **待办**：无（流程类决策，见 `AGENTS.md` §6）。

## D-007 首阶段反馈仅做调试界面叠加（提案）

- **背景**：反馈可以只做界面高亮，也可以做虚拟显示板甚至硬件灯效。
- **提案**：P0 的反馈输出为 `FeedbackCommand{target:"ui_overlay"}`，虚拟显示板与硬件反馈留到后续批次。
- **影响**：S7 工作量可控；`target` 枚举已在协议中预留。
- **待办**：确认 Q6；若首阶段要求虚拟显示板，需在 ROADMAP 增加独立任务。

## D-008 识别层只输出候选，不做结论与过滤

- **背景**：过早过滤会掩盖漏检与误检，也让调参无据可依。
- **决策**：识别层输出全部候选（含 `unknown_card` / `occluded` / `clipped` / `ambiguous`），排序、去重、取舍一律在排列层并留诊断。
- **影响**：调试界面能看到「为什么丢了一张卡」；带宽与数据量略高。
- **待办**：性能成为瓶颈时，在识别层加「只降采样不丢弃」的选项。

## D-009 运行记录用 JSONL（提案）

- **背景**：需要一次性保存一帧/一次运行的所有层产物，供回放与回归。
- **提案**：一次运行一个 JSONL 文件，首行 `RunHeader`，其后按产出顺序写各层对象与事件。
- **影响**：可流式写入、可逐行 diff；不足是单文件内查询需要工具。
- **待办**：确认 Q8 与存放位置（是否入库 fixtures）。

## D-010 人工测试与反馈入口复用 GitHub Issues（已定）

- **背景**：首阶段不引入外部反馈系统。
- **决策**：人工测试与反馈统一走 GitHub Issues，模板 `.github/ISSUE_TEMPLATE/hardware-test.md`。
- **影响**：无需额外基础设施；证据（照片、日志）以附件形式留在 Issue 中。
- **待办**：Issue 中回填「对应版本」，使证据与 commit/PR 绑定。

## D-011 LB-001 骨架暂按 Python 3.11 + pytest 落地（提案，待 D-004 确认）

- **背景**：LB-001 的验收要求「README 命令可原样执行、一条命令跑全量测试并输出用例数 ≥1、断言失败时非零退出」，必须落到具体语言与命令；D-004（Python 3.11 + OpenCV + pytest）仍是提案，仓库所有者尚未确认 Q9。
- **决策**：骨架按 D-004 的提案方向落地，标记为**临时**选择：Python（`requires-python >=3.11`）、`src/` 布局、setuptools + `pyproject.toml` 声明依赖、pytest 作为测试框架、`scripts/check.sh` 作为唯一本地检查入口、GitHub Actions 跑同一脚本。**D-004 状态不变，仍为「提案」。**
- **影响**：仓库首次出现可执行代码与 CI。骨架不含业务逻辑，若最终换成其他语言（如 TypeScript），替换范围仅为 `pyproject.toml`、`src/liveblocks/`、`tests/`、`scripts/check.sh`、`.github/workflows/ci.yml`；`fixtures/` 与 `docs/` 不受影响，也不会把语言代价传导到 LB-002+ 的设计。
- **待办**：仓库所有者确认 Q9 / D-004 后，把 D-004 置为「已定」并把本条标「已被 D-004 取代」；若选其他语言，按上面列出的替换范围新增一条 ADR 并重做骨架，届时本条作废。
