## D-001 首阶段以纯软件闭环为目标

- **背景**：仓库目前只有初始 README；硬件选型、电源、引脚均未验证，直接做硬件会把不确定性混进架构验证。
- **决策**：第一阶段只做纯软件闭环：合成卡片图像 → 识别 → 排列 → 解析 → IR → 模拟执行 → 调试界面。真实摄像头与硬件执行放到后续批次。
- **影响**：所有 P0 任务的验收都不依赖硬件；模拟执行器必须与未来硬件后端共用同一事件流格式。
- **待办**：在 `backend.hw` 实现时补一次「同 IR 双后端一致性」验证（LB-013）。

## D-002 层间契约用 JSON，IR 与事件流为唯一落盘边界

- **背景**：链路有 7 个阶段、多种实现可能（Python/TS/固件），需要可序列化、可回归、可人工审阅的边界。
- **决策**：层与层之间只通过 `docs/PROTOCOL.md` 定义的对象交互；跨语言、落盘、回归一律以 `Ir` / `ExecEvent` / `ExecResult` 为准。
- **影响**：模块可独立替换与独立测试；调试界面与回归测试只消费契约，不读内部状态。
- **待办**：协议冻结前补齐 schema 校验工具与 golden 文件（LB-006、LB-009）。

## D-003 协议文档以草案版本化，只做加法式演进

- **背景**：文法与 IR 都会反复调整，早期若宣称稳定会误导下游。
- **决策**：`docs/PROTOCOL.md` 长期标注「草案 v0.0.x」；只加字段不改语义时提升 `minor`，破坏性变更提升 `major` 并在此文件记录迁移说明。消费者必须容忍未知字段与未知枚举。
- **影响**：早期实现可以并行推进；不足是接口随时可能变动，文档必须同步维护。
- **待办**：每次格式变更在同一 PR 内更新协议版本与 `docs/PROGRESS.md`。

## D-004 实现语言与运行时（提案，未定）

- **背景**：需要选定 MVP 骨架的语言，影响 LB-001 的具体内容。
- **提案**：Python 3.11+ + OpenCV（ArUco 支持完整、原型快），测试用 pytest；调试界面先用本地 Web 前端或轻量 GUI。
- **备选**：TypeScript/Node（前端与界面统一，但 ArUco 生态较弱）。
- **影响**：等待确认期间，LB-001 的验收只写「命令可执行、测试可跑」，不绑定具体命令实现。
- **待办**：由仓库所有者确认后再落地 LB-001 的脚本细节。**未确认前不得擅自锁定语言。**
- **进展（2026-11-23）**：LB-001 骨架已按本提案以 Python 3.11 + pytest 落地，作为**临时**选择记录在 D-011；本条仍为「提案」，语言未锁定。

## D-005 P0 文法取最小集（提案，未定）

- **背景**：文法表达力决定了 AST、IR 与执行器的规模。
- **提案**：P0 只支持「语句序列 + 字面参数」，即卡片按行顺序执行，不引入变量、条件、循环、函数。
- **影响**：解析器与执行器都能在一两个任务内跑通；后续扩展需要提升 `grammar_version`。
- **待办**：与 Q4/Q5 一并确认；若改为立即执行型指令，需重写 D-002 的 IR 语义说明。

## D-006 单并发 + 人工合并

- **背景**：多个代理并行改同一批文件会产生冲突与不可追溯的合并。
- **决策**：同一时间只推进一个实现任务；所有 PR 由人审阅合并，代理不自动合并、不绕过评审、不开 auto-merge。
- **影响**：吞吐受限但历史干净、可回滚。
- **待办**：无（流程类决策，见 `AGENTS.md` §6）。

## D-007 首阶段反馈仅做调试界面叠加（提案）

- **背景**：反馈可以只做界面高亮，也可以做虚拟显示板甚至硬件灯效。
- **提案**：P0 的反馈输出为 `FeedbackCommand{target:"ui_overlay"}`，虚拟显示板与硬件反馈留到后续批次。
- **影响**：S7 工作量可控；`target` 枚举已在协议中预留。
- **待办**：确认 Q6；若首阶段要求虚拟显示板，需在 ROADMAP 增加独立任务。

## D-008 识别层只输出候选，不做结论与过滤

- **背景**：过早过滤会掩盖漏检与误检，也让调参无据可依。
- **决策**：识别层输出全部候选（含 `unknown_card` / `occluded` / `clipped` / `ambiguous`），排序、去重、取舍一律在排列层并留诊断。
- **影响**：调试界面能看到「为什么丢了一张卡」；带宽与数据量略高。
- **待办**：性能成为瓶颈时，在识别层加「只降采样不丢弃」的选项。

## D-009 运行记录用 JSONL（提案）

- **背景**：需要一次性保存一帧/一次运行的所有层产物，供回放与回归。
- **提案**：一次运行一个 JSONL 文件，首行 `RunHeader`，其后按产出顺序写各层对象与事件。
- **影响**：可流式写入、可逐行 diff；不足是单文件内查询需要工具。
- **待办**：确认 Q8 与存放位置（是否入库 fixtures）。

## D-010 人工测试与反馈入口复用 GitHub Issues（已定）

## D-012 LB-002 合成卡片生成器：零依赖渲染 + 入库字典/版式 + 真值 schema

- **背景**：LB-002 要求「按卡片字典与版式定义生成 ArUco 卡片图像，输出图像 + 真值 JSON」，
  并且验收里有「给定固定随机种子，生成结果字节可复现」。同时 LB-003 会拿 OpenCV 检测这批
  合成图里的标记，所以生成出来的必须是**真的 ArUco 码字**，不能是「长得像标记的方块」。
- **决策**：
  1. 生成器作为**实现模块**放在 `src/liveblocks/synth/`（`fixtures/scenes/` 只是它的输出），
     与 `docs/ARCHITECTURE.md` §2 中「fixtures 负责合成卡片图像生成」的边界一致。
  2. **运行时零依赖**：自带 PNG 编码（`zlib` + `filter=None` + 固定压缩级别）、自带 ArUco
     位表（`DICT_4X4_50` 的 50 个码字入库为 JSON）、自带点阵字体（入库为 JSON 位图），
     安装即可生成，不需要 OpenCV / PIL / numpy。
  3. 相机用**针孔 + 无畸变**模型（`fx/fy/cx/cy`），位姿为相机坐标 `(x_mm, y_mm, z_mm)` +
     `yaw/pitch/roll_deg`；`yaw` 是面内旋转，`pitch/roll` 是透视倾斜。
  4. 「卡片字典」与「版式定义」是**数据文件**（`src/liveblocks/data/`）：卡片字典登记
     `card_id → marker_id + card_face`；版式定义分 `card_layouts`（卡面怎么画）与
     `scene_presets`（摆几张卡、位姿、遮挡物、光照、位姿抖动）。
  5. 真值 schema 版本 `0.0.1`、`kind: "SyntheticCardScene"`：角点顺序固定左上/右上/右下/左下
     并按卡片/标记自身坐标系解释（对齐 `docs/PROTOCOL.md` §3.1），`status` 取
     `ok|clipped|occluded`（`unknown_card`/`ambiguous` 属于识别层结论）；位姿记录的是
     **抖动之后**的实际位姿。
  6. 一个随机种子同时驱动位姿抖动与光照噪声，消耗顺序固定（抖动 → 逐卡绘制 → 光照），
     因此同种子必然得到同字节。
- **影响**：
  - 字节可复现性只依赖标准库，不受 OpenCV/PIL/numpy 版本影响（PNG 压缩仍受 zlib 实现影响，
    测试因此同时校验「PNG 字节」与「解码后像素」，并在 `pixel_sha256` 里记录与压缩无关的指纹）。
  - CI 不需要装 OpenCV；`tests/test_synth_dictionary.py` 在装了 `.[aruco]` 时会把 OpenCV 当作
    独立实现逐位核对入库位表，没装则跳过。
  - 代价是 PNG 写盘、位表、字体都要自己维护；渲染是纯 Python，单场景约 1.5 秒、6 个 fixtures
    约 9 秒，测试可接受。
  - 已知局限：只出灰度图、无镜头畸变、无运动模糊、遮挡物只支持凸四边形、无材质/阴影。
- **待办**：
  - Q1（ArUco 字典与标记尺寸）仍是待决：当前临时固定 `DICT_4X4_50` + 16 张卡 + 24 mm 标记。
    改字典只需改 `data/` 与版式并重新生成 fixtures。
  - Q2（单标记 vs 四角标）未定：当前按「一张卡一个标记」实现，`marker_ids` 数组的语义留给 LB-003。
  - 真值 schema 若被 LB-003/LB-004 需要扩展，按 `docs/DECISIONS.md` §D-003 的加法式演进处理。

## D-013 LB-003 识别层：零依赖检测与译码 + 亚像素边缘细化（OpenCV 仅作可选交叉核对）

- **背景**：LB-003 要「对 LB-002 的 fixtures 跑识别」，而 LB-002 的生成器是**零运行时依赖**的
  （D-012），CI 只装 `.[dev]`（没有 numpy / OpenCV）。D-004 的提案里写的是「Python + OpenCV」，
  但那条仍是提案，且真装上 OpenCV 会让「识别结果能否复现」依赖第三方版本。另一方面，纯标准库
  做 ArUco 检测是可行的：标记是 4×4 码字 + 1 模块黑边，几何简单。
- **决策**：识别层（`src/liveblocks/vision/`）**只用标准库**，管线为
  1. 局部自适应二值化（积分图求窗口均值）；
  2. 8 连通域 → 一个标记的黑边与内圈黑模块天然连成一个连通域；
  3. 凸包 → 逐点删「三角形面积最小」的顶点化简成四边形 → 凸性/边长/长宽比/填充率筛选；
  4. **亚像素边缘细化**：沿每条边的外法向按 0.2 px 采样灰度，取「灰度 = 黑白中点」的过渡点拟合
     直线、相邻直线求交（把角点误差从约 1.5 px 降到 0.4 px）；
  5. 6×6 模块采样 + 归一化 4 点单应（Hartley 归一化，避免小四边形的透视项被放大）+ 码字比对
     （4 个 90° 旋转，最多 1 位错，且黑边必须整圈偏暗）。
  OpenCV 只作为**可选**交叉核对（`.[dev,aruco]` extra，`tests/test_vision_opencv.py` 在没装时跳过），
  用它的 `ArucoDetector` 独立验证「检出集合」与「角点位置」。
- **影响**：
  - CI 不需要装 OpenCV，识别结果只依赖标准库与 zlib，跟 LB-002 的可复现性口径一致；
  - 与 OpenCV 的实测对照：`normal` / `low-light` / `slight-rotation` / `multi-row` 四个完整可见场景
    标记 id 集合完全一致；共有标记的角点差 ≤ 2 px；
  - 已知分歧（写进测试断言，行为变了会失败）：`clipped` 里被下边界切到的标记 13 我们能读出、
    OpenCV 漏掉；`overlap` 里被纸片压住的标记 6 OpenCV 能读出、我们判「不可译码」；
  - 代价：纯 Python 单帧约 0.3~0.5 秒（640×480），只适合 P0 的合成图与回归，实时性留给后续任务；
  - 局限：只有 1 模块宽黑边的 4×4 字典；不做多尺度检测（标记小于约 8 px 边长会漏）；不估计镜头畸变。
- **待办**：Q1（字典规模/标记尺寸）与 Q2（单标记 vs 四角标）定了之后，扩展 `aruco_dictionaries.json`
  与检测器；真实摄像头的鲁棒性（运动模糊、反光、透视更大）属于 LB-010 / LB-020。

## D-014 LB-003 状态/置信度/朝向/诊断码的定义，以及 `PROTOCOL.md` §3 的缺口清单

- **背景**：协议 §3.2 只给了 `status` 的 5 个枚举值与字段名，没有定义「什么情况算 `clipped`」
  「confidence 怎么算」「`orientation_quadrant` 从哪来」，也没有给 S2 对象留 `diagnostics` 槽位；
  而 §0 又要求未知值降级为 `unknown` 并体现在诊断里。LB-003 必须把口径写死，否则下游无法回归。
- **决策**：
  1. **status 判定与优先级**（单字段只能给一个值，其余事实进诊断）：
     `unknown_card` > `clipped` > `occluded` > `ok`。
     - `unknown_card`：标记码字在 ArUco 字典内、但没有在卡片字典登记；
     - `clipped`：由标记 + 卡片注册版式外推出的卡片四角越出画面（口径与 LB-002 真值一致：
       `0 <= x < width`），或标记自身触及画面边界；
     - `occluded`：码字有 1 位残余位错仍能唯一识别，或检出形状但身份不可读；
     - `ambiguous`：位串在多个标记之间等距（本字典最小码距为 4，因此只可能出现在容错比对里）。
  2. **卡片范围来自「采集配置」**：协议 §11 明确卡片字典的登记格式未定，因此识别层复用 LB-002 的
     卡面版式（`synth_layouts.json` 的 `card_layouts`：卡片尺寸、标记尺寸、标记中心）当作**物理注册
     信息**，用命令行 `--card-layout` 指定（等同于「这次用的是哪种卡纸」）。**不用真值里的卡片身份
     或位姿**。逐卡版式/朝向覆盖能力留在 `CardRegistry` 的参数里，等 Q1/Q2 定了再进数据文件。
  3. **confidence**（可比较，公式写死）：`0.6 × 模块黑白对比度 + 0.4 × (1 - 位错/4)`，取 [0,1]；
     黑色基准取黑边均值、白色基准取内圈最亮 5 个模块的均值，对比度按 128 灰阶差归满。身份不可读的
     候选把置信度封顶 0.5（读不出是谁就不该高置信）。实测：`normal` 1.0、`low-light` 约 0.72。
  4. **orientation_quadrant**：0–3，表示卡片相对标记坐标系的 90° 倍数旋转，来源是**注册信息**
     （当前所有卡都是 0，因为卡面版式里标记与卡片同轴）。身份不可读（`occluded` / `ambiguous`）或
     标记未登记（`unknown_card`）时**不输出该字段**——协议没有「方向未知」的表示法。
  5. **本实现新增的诊断码**（§9 的 `LB-V0xx` 区间，`LB-V002` 沿用 §9 示例语义）：
     `LB-V001` 标记未在卡片字典登记、`LB-V002` 标记被画面边界裁切、`LB-V003` 检出了标记形状但码字
     不可靠、`LB-V004` 同一标记重复检出（保高置信、留痕）、`LB-V005` 码字在多个标记间无法区分、
     `LB-V006` 由标记外推的卡片范围越出画面。
  6. **输出不做排序**（协议 §3.2 要求）：候选顺序就是连通域扫描顺序；也**不丢弃**低置信候选（D-008）。
- **影响**：识别层的每条结论都能在诊断里找到依据；`status` 的多事实冲突（例如未登记又越界）会同时
  留下 `LB-V001` 与 `LB-V006`。代价是 S2 对象多了一个可选 `diagnostics` 数组，属于加法式扩展
  （§10 规则 1），消费者必须容忍。
- **发现的协议缺口（本 PR 只报告、不改 `docs/PROTOCOL.md`）**：
  1. §3.1 / §3.2 **没有 `diagnostics` 字段**，但 §0 要求未知值「必须在诊断中体现」——实现按加法式
     补一个可选数组，建议协议显式定义；
  2. §3.2 的 `status` 是单值枚举，无法表达「既未登记又被裁切」，需要约定优先级或改成数组；
  3. `orientation_quadrant` 没有「未知」表示法（建议允许 `null` 或 `unknown`）；
  4. §0 说 `schema_version` 是 `major.minor`，但 §2~§7 的所有示例都是三段式 `0.0.1`；
  5. §0 说「角度逆时针为正」，而相机/图像坐标 y 向下，因此「绕 +z 的右手法则角」在画面上是顺时针；
     §3.1 的 `angle_deg` 与 `pose.yaw_deg` 需要各自的约定说明（本实现统一成「画面上的逆时针为正」，
     与 LB-002 真值里 `in_plane_angle_deg`（顺时针为正）差一个负号，测试里显式处理）；
  6. §3.2 没有 `card_id`，但卡片字典自称「`card_id` 是链路里所有下游层引用卡片身份的键」——实现
     输出里加了 `card_id`（加法式），或者协议应明确「下游用 `marker_ids` + 字典反查」；
  7. §3.1 的 `pose` 没写是否必填，也没写精度要求；本实现只在给了内参且标记可见边长 ≥ 24 px 时输出。
- **待办**：协议冻结前把上面 7 条并进 §3（由仓库所有者决定取舍）；届时更新本文与实现。

## D-015 LB-004 排列层：卡距自适应、行/列与阅读方向的关系、朝向归一、去重与诊断码

- **背景**：Issue #11 要求「分簇、阅读方向排序、朝向归一、去重、歧义诊断」，输出符合
  `docs/PROTOCOL.md` §4 的 `Layout`。但 §4 只给了字段与一个示例：**没有**定义排序依据怎么留痕、
  `reading_direction` 各取值下 `rows`/`slots` 的几何含义、`orientation_quadrant` 在排列层的
  归一化基准、间距/重复的阈值口径，也没说「哪些候选该被排除」。§3.2 的候选里唯一的位置信息是
  `center_px`，**没有卡片物理尺寸**，而阈值必须有个长度尺度。这些口径不写死就没法回归。
- **决策**（实现落在 `src/liveblocks/layout/`：`protocol.py` 数据模型与校验、`arrange.py` 算法、
  `report.py` 自检报告；只消费 §3.2 的 `CardCandidateList`，不解析语法）：
  1. **尺度自适应**：「典型卡距」`pitch_px` = 各可用候选到最近邻欧氏距离的**中位数**（去重后重估
     一次）；所有阈值都是它的倍数，可用 `LayoutOptions.pitch_px` / `--pitch-px` 显式覆盖。
     默认值：重复判定 0.35、行切分 0.75、行内跨度上限 1.0、行边界存疑 1.2×行切分阈值、
     行内间距歧义 0.6。
  2. **分簇**：沿阅读方向的「换行轴」做一维间隙聚类——相邻候选在该轴上的坐标差大于行切分阈值
     就起新的一行。行按换行轴坐标排序（横排自上而下、`ttb_ltr` 的列自左而右）。
  3. **`rows`/`slots` 与 `reading_direction` 的关系**（§4 只说「具体与阅读方向的关系由 S3 解释」，
     这里按此授权定义）：`ltr_ttb`/`rtl_ttb` 的「一行」是画面上的横排，行内按 x 递增 / 递减；
     `ttb_ltr`（自上而下成列、列自左而右）的「一行」是画面上的一列，行内按 y 递增、行与行按 x
     递增。`row_index` / `slot_index` 始终按数组顺序从 0 连续。
  4. **朝向归一**：槽位上的 `orientation_quadrant` = `(候选象限 − 阅读方向的正立象限) mod 4`，
     0 表示「按当前阅读方向正立可读」。水平阅读的正立象限是 0（图像正立），`ttb_ltr` 是 1（卡片
     顺时针转 90° 才算正立）。非 0 时**保留原值并报 `LB-L005`**，不静默旋转、不丢弃。
  5. **过滤**：只有 `status ∈ {ok, clipped}` 的候选进排列；`unknown_card` / `occluded` /
     `ambiguous` 用 `LB-L003` 逐个点名后排除。协议 §3.2 要求识别层不排序、不丢弃，因此「不采用」
     的结论必须在排列层留痕（承接 D-008）。
  6. **去重**：身份相同（优先 `card_id`，缺省退回 `card_face`）**且**圆心距 ≤ 0.35×卡距的候选视为
     同一张卡的重复检出，保留置信度最高者（同置信度时按「更靠上、更靠左、id 更小」保证确定性），
     被移除者由 `LB-L002` 点名。**同卡面但不重合的两张卡是合法的重复卡，不去重。**
  7. **诊断码**：`LB-L001`（行内间距歧义）、`LB-L002`（重复被移除）沿用 §9 语义；新增
     `LB-L003`（身份未知、未纳入排列）、`LB-L004`（行分组边界存疑：行间隙接近切分阈值，或行内
     换行轴跨度超过卡距——即「两行被误判为一行」）、`LB-L005`（相对阅读方向非正立）。都在 §9 的
     `LB-L0xx` 区间。
  8. **加法式扩展**：`Layout` 多一个可选 `basis`，记录卡距、阈值、阅读坐标系约定、每行候选 id /
     行中心 / 跨度与候选计数（去重移除数、身份未知数），供调试界面（LB-008）与回归使用；槽位字段
     **严格按 §4 的 7 个字段**输出（不加 `card_id`），置信度保留 3 位小数、坐标四舍五入成整数像素
     （§0 要求像素为整数）。
- **影响**：
  - 排列层完全不依赖 LB-003 的内部几何（角点、位姿），只吃 §3.2 的字段，因此可以用「手写的候选
    JSON」当夹具测试（`fixtures/layouts/`）；真实识别输出的快照夹具另有测试保证与上游一致。
  - 阈值全部是卡距的倍数，桌面尺度和相机距离变了不用改参数；代价是**只有两张卡、或两行贴得比卡
    距更近时无法判歧义**（自适应尺度退化），这时需要用 `--pitch-px` 显式给预期卡距。
  - 已知局限：`ttb_ltr` 的「一行是一列」是本实现对 §4 的解释（见上第 3 条），解析层若按「横排
    才叫行」实现需要对齐；朝向归一依赖注册象限，而当前 LB-003 的象限来自注册信息（恒为 0），
    真正的「卡片转 90°」尚未在实测中出现。
- **发现的协议缺口（本 PR 只报告、不改 `docs/PROTOCOL.md`）**：
  1. §4 没定义「排序依据」怎么表达（示例里只有每个槽位的 `candidate_id`）——本实现加 `basis`；
  2. §4 没定义 `ttb_ltr` 下 `rows`/`slots` 的几何含义，也没说 `row_index`/`slot_index` 是否必须
     从 0 连续（本实现按数组顺序强制连续，这样「可追溯」才成立）；
  3. §4 与 §3.2 都没有排列层可用的长度尺度（卡片物理尺寸 / 预期卡距 / 每张卡的范围），只能从
     候选位置自适应估计；建议在 S2 或 `Frame`/采集配置里带上卡片尺寸或预期卡距；
  4. §3.2 的 `orientation_quadrant` 没有「未知」表示法，§4 也没给排列层的归一化基准（承接
     D-014 第 3 条）；
  5. §4 的槽位没有 `card_id`（LB-003 在 S2 加了加法式 `card_id`），解析层要卡片身份只能靠候选 id
     反查或再加一次加法式字段；
  6. §9 的 `LB-L0xx` 只举了 `LB-L001`/`LB-L002`，没有「候选被排除」「行分组存疑」「朝向非正立」
     的码，本实现按区间自增；
  7. §4 没规定 `confidence` 精度与 `x_px`/`y_px` 的取整方式（本实现：置信度 3 位小数、坐标四舍
     五入为整数像素）。
- **待办**：协议冻结前把上面 7 条并进 §4（由仓库所有者决定取舍）；Q3（排列语义：单行/多行/棋盘）
  确认后，若采用二维棋盘或显式接线，需要扩展 `Layout` 的行列模型与本文第 2/3 条。

## D-016 LB-005 语法层：P0 文法、`span`/`origin` 约定、`LB-P0xx` 码表与 §5 的缺口

- **背景**：Issue #14 要求「最小文法（P0 定为「语句序列 + 字面参数」），错误定位到行/槽位/卡片」，
  输出符合 `docs/PROTOCOL.md` §5 的 `Ast`。但 §5 只有一个示例两句约定：**没有**定义文法产生式、
  卡面到「命令/字面量」的映射、`span` 是否闭区间、跨行节点（`Program`）的 `span` 怎么写、多卡节点
  的 `origin` 怎么写、每条命令收几个参数，也没给 `LB-P0xx` 的码表（§9 只举了 `LB-P003` 一个例子）。
  D-005 定了「语句序列 + 字面参数」的方向，但仍是提案，没落到可执行的规则。
- **决策**（人类可读定义见 `docs/GRAMMAR.md`，机器可读的同一份在
  `src/liveblocks/parser/grammar.py`；`tests/test_parser_grammar.py` 与 `liveblocks parse report`
  逐项核对两者一致）：
  1. **文法**：`Program ::= Statement*`；`Statement ::= Command Literal*`；
     `Command ::= command_card`；`Literal ::= number_card`。**一行 = 一条语句**，语句顺序 = `rows`
     顺序，参数顺序 = 槽位顺序；没有任何行 → 空程序（合法）。`grammar_version = 0.0.1`。
  2. **卡面角色按卡片字典推导**（不写死）：`action` → 命令；`number` → 字面量（值取
     `number-<整数>` 的后缀）；`operator` → 运算符（P0 不支持）；`control` → 只有 `wait` 当普通
     语句（不引入分支/循环），`repeat` / `if` / `end` 需要「块」，超出 P0。字典新增卡时角色自动
     跟上；文档里的角色表必须同步列全（否则测试失败）。
  3. **不检查参数个数（arity）**：§5 与 D-005 都没有出处，P0 一律接受零个或多个字面参数；
     arity 属于 IR 语义（LB-006）。要冻结 arity 必须提升 `grammar_version`。
  4. **`span` 用闭区间**：`slot_from`/`slot_to` 都指向真实槽位；单行节点照 §5 写
     `{row, slot_from, slot_to}`，跨行的 `Program` 写 `{row_from, row_to, slot_from, slot_to}`
     （覆盖首行到末行、槽位 0 到最宽行的最后一个槽位）。
  5. **`origin` 每个节点都有**：单卡节点照 §5 用 `{candidate_id, card_face}`；`Program` 用
     `{candidate_ids, card_faces}` 列出参与语句的全部卡片（空程序是两个空数组）。
  6. **`Ast` 加 `frame_id`**（加法式）：把语法树指回它来自哪一帧，供 LB-008/LB-009 回溯。
  7. **错误策略：整行丢弃、只报一条、定位到第一个违约槽位**。一条语句（一行）的任何槽位违约就
     整条丢掉，诊断的 `span` 指向那个槽位、`origin` 与 `candidate_ids` 指向那张卡；同一行不再产生
     第二条诊断（避免级联误报），其余行照常解析 → 非法输入得到**部分 AST** 而不是异常（
     「不崩溃」）。
  8. **诊断码（§9 的 `LB-P0xx` 区间）**：`LB-P001` 语句缺命令卡、`LB-P002` 参数位置不是字面卡、
     `LB-P003` 槽位为空或卡面未知（沿用 §9 示例语义并扩展）、`LB-P004` 控制流卡超出 P0 文法、
     `LB-P005` 运算符卡超出 P0 文法。`severity` 一律 `error`，每条都带 `span` 与 `origin`。
     **输入本身不是合法 §4 文档时抛 `ValueError`**（CLI 非零退出），不伪装成 `LB-P0xx`。
  9. **不复制上游诊断**：`Layout.diagnostics`（`LB-L0xx`）留在排列层，`Ast.diagnostics` 只有
     `LB-P0xx`；一次运行的各层对象都会进运行记录（§8），信息不丢。
- **影响**：
  - 语法层只吃 §4 的字段（`row_index` / `slot_index` / `candidate_id` / `card_face`），不依赖
    卡片像素坐标，因此夹具可以是手写的 Layout JSON（`fixtures/ast/`）；真实排列输出的快照另用
    测试保证与上游一致。
  - 「一行 = 一条语句」意味着**画面上的一行就是语法上的一条语句**：这与 D-015 对 `ttb_ltr`
    「一行是画面上的一列」的解释兼容（本层只看 `rows`/`slots` 顺序，与几何无关），但若将来把
    「一行」改成严格横排，解析层的顺序语义要一起改。
  - 丢弃整行是最保守的错误恢复方式：非法样例不会产出「半条语句」误导下游；代价是被丢掉那行里
    的合法卡不在 AST 里（诊断的 `span`/`origin` 能指回去，且原 Layout 仍在运行记录里）。
- **发现的协议缺口（本 PR 只报告、不改 `docs/PROTOCOL.md`）**：
  1. §5 的示例自相矛盾：`Program.span` 写 `{row:0, slot_from:0, slot_to:2}`，但示例的 `rows[0].slots`
     只有 2 个槽位（0..1）；本实现按闭区间取「最后一个槽位下标」；
  2. §5 没写跨行节点的 `span`，也没写多卡节点的 `origin`（本实现加 `row_from`/`row_to` 与
     `candidate_ids`/`card_faces`）；
  3. §5 正文要求「每个节点都带 `span` 与 `origin`」，但示例的 `Number` 节点没有 `origin`（本实现
     一律输出，校验器也要求有）；
  4. §5 没有 `frame_id`（或任何上游引用），语法树无法自查来自哪一帧（本实现加法式补上）；
  5. **参数个数（arity）没有出处**：§5 与 D-005 都没说每条命令收几个参数，P0 不做判断（留给
     LB-006）；建议在协议里给一张「命令 → 参数元数」表；
  6. §9 只给了 `LB-P003` 一个示例，`LB-P0xx` 的其余码由本实现按区间自增；
  7. §5 说「`node` 取值集合是开放枚举」，但没给「未知节点名该不该继续解析/如何降级」的口径；
     本实现的校验器遇到未知节点名只要求 `span` + `origin`；
  8. 字面量只有整数：字典里只有 `number-1/2/3/5`，小数/负数/字符串字面量没有卡片可表达，
     因此 `Number.value` 是整数。
- **待办**：协议冻结前把上面 8 条并进 §5/§9（由仓库所有者决定取舍）；D-005 与 Q4（文法表达力）
  确认后，若 P0 要加表达式或控制流，必须提升 `grammar_version` 并同步扩 `docs/GRAMMAR.md`
  的产生式、卡面角色表与诊断码。

## D-017 LB-006 规范化 IR：`op` 取卡面、元数表、`limits` 缺省值、`LB-I0xx` 码表与 §6 的缺口

- **背景**：Issue #16 要求「AST → 确定性 IR，schema 校验，缺省值填充，`limits` 显式化」，输出符合
  `docs/PROTOCOL.md` §6 的 `Ir`。但 §6 只有四句约定（确定性、`limits` 必须显式、`op` 只能来自文法
  定义、未知 `op` 是规范化错误）和一个示例：**没有**说卡面怎么变成 `op`（示例写 `op: "move"`，卡面
  却叫 `move-forward`）、每条命令收几个参数、参数与单位叫什么、`limits` 的缺省值是多少、`step_id`
  怎么编号、`args` 是什么形状，也没给 `LB-I0xx` 的其它码（§9 只举了 `LB-I001` 一个例子），更没给
  schema 文件（D-015/D-016 都写着「完整的 schema 工具留给 LB-006/LB-009」）。D-016 第 3 条明确把
  arity 留给本任务。
- **决策**（人类可读的定义见 `docs/IR.md`，机器可读的同一份在 `src/liveblocks/ir/ops.py` 与
  `src/liveblocks/data/ir_schema.json`；`tests/test_ir_docs.py` 与 `liveblocks ir report` 逐项核对
  两者一致）：
  1. **`op` 直接取卡面**（`Command.name` 原样）。依据是 §6 自己那句「只允许 `op` 取值来自文法定义」，
     而文法里的命令名就是卡面（D-016 第 2 条）。示例里的 `op: "move"` 与卡面 `move-forward` 对不上，
     是 §6 自身的缺口：要让 `move-back` 也叫 `move` 就得替它发明「负距离」之类的语义，超出本单范围，
     因此**不猜**，只报缺口（见下第 1 条）。`move-back` / `turn-left` 等方向信息留在 `op` 里。
  2. **元数（arity）与参数名/单位按「卡面上写的意思」取最小集**：`move-forward` / `move-back` 收
     1 个 `distance`（单位 `cell`，§6 示例用的就是这个单位）、`turn-left` / `turn-right` 收 1 个
     `angle`（单位 `quarter_turn`）、`wait` 收 1 个 `duration`（单位 `tick`）、`jump` / `pick` /
     `drop` 不收参数。P0 每个 `op` 至多一个数值参数，因此 `args` 的形状固定为
     `{"<参数名>": <整数>, "unit": "<单位>"}`，零元 `op` 用空对象 `{}`（对齐 §6 示例的
     `{"distance": 1, "unit": "cell"}`）。单位只是标签，物理换算（尤其 `tick` ↔ 毫秒）属于 LB-007 / Q5。
  3. **参数个数不符是规范化错误**：`LB-I002`，该语句不进 IR，**不截断、不补零、不猜默认参数**——
     这正是 D-016 第 3 条把 arity 推给本任务时要的结论。**这条规则会让真实链路的某些 P0 程序降级**：
     `fixtures/ast` 的 `valid-basic`（`turn-left 2 3`）与 `from-overlap-cards`（单张 `move-back` 没带
     数字卡）在 IR 阶段各报一条 `LB-I002`。这是如实结果，不是 bug：语法层不管 arity，IR 才管。
  4. **`op` 表从卡片字典推导 + 显式登记元数**：op 表必须覆盖字典里全部 `command` 角色卡面，
     `op_table_gaps()` 会把「字典有、表里没有」与「表里有、字典没有」都报出来；字典新增一张 action 卡
     后必须回来扩表（元数不能猜），否则 `ir report` 与测试失败。
  5. **`limits` 在规范化阶段就填**（范围项要求「显式化」），缺省值取 §6 示例的
     `max_steps = 1000` / `timeout_ms = 5000`；两者必须是 ≥ 1 的整数（0 / 负数算配置错误，抛
     `ValueError`）。可用 API 参数或 CLI `--max-steps` / `--timeout-ms` 覆盖，覆盖值照样写进 IR。
     **「步数超限 / 超时」不在本层判定**：那是执行层的 `ExecResult.status = limit_exceeded/timeout`
     （§7.2，LB-007）。
  6. **`step_id` 密集编号**：`s0` / `s1` / …，按**产出的**步骤顺序（与 D-015 起强制的 `row_index` /
     `slot_index` 连续口径一致）。被丢弃的语句不占编号，诊断里的 `span` 指回原行/原槽位。
  7. **`source` 照 §6 示例写 `{"row", "slot"}`**，取 `Command.span` 的起始行与起始槽位；不加
     `candidate_id` 之类的加法式字段（保守，且诊断的 `candidate_ids` 已经能逐卡回溯）。
  8. **诊断码（§9 的 `LB-I0xx` 区间）**：`LB-I001` 未知 op（沿用 §9 示例语义，含文法外的控制流卡
     `repeat` / `if` / `end`）、`LB-I002` 参数个数不符、`LB-I003` 语句节点不受支持（§5 的 `node`
     是开放枚举）、`LB-I004` 参数不是字面量（取不到整数）。`severity` 一律 `error`，每条带 `span`
     与 `candidate_ids`。**一条语句最多一条诊断**，检查顺序固定（节点种类 → op → 参数 → 元数），
     不做级联。**输入本身不是合法 §5 文档时抛 `ValueError`**（CLI 非零退出），不伪装成 `LB-I0xx`。
  9. **不复制上游诊断**：`Ast.diagnostics`（`LB-P0xx`）留在语法层，`Ir.diagnostics` 只有 `LB-I0xx`。
  10. **schema 入库**：`src/liveblocks/data/ir_schema.json`（JSON Schema draft 2020-12，随 wheel 安装，
      `liveblocks.data` 的 `*.json` 已在 `pyproject.toml` 里声明），配一个零依赖的最小校验器
      （只支持 schema 用到的那一小撮关键字，schema 里出现不支持的关键字测试就失败）；schema 表达不了
      的语义检查（op↔args、`step_id` 密集、诊断码区间）放在 `validate_ir`。装得上 `jsonschema` 时
      `tests/test_ir_protocol.py` 用它当独立实现交叉核对，CI 只装 `.[dev]` 时该例自动跳过。
  11. **确定性**：所有对象按固定顺序构造、序列化只走 `Ir.canonical_text()`
      （`ensure_ascii=False`、`indent=2`、不排序键、结尾一个换行），数值只有整数、无时间戳/随机量，
      诊断顺序 = 语句顺序。验收用三重证据：同进程两次相等、不同 `PYTHONHASHSEED` 的子进程输出相等、
      与入库 golden 逐字节相等。
- **影响**：
  - IR 只吃 §5 的字段（`name` / `args[].value` / `span` / `origin`），因此夹具可以是手写的 Ast JSON
    （`fixtures/ir/asts/`）；三个上游快照夹具另有测试保证与 LB-005 一致。
  - 因为 arity 变严，真实链路上「只放了一张命令卡、没放数字卡」的程序会在 IR 阶段被点名（`LB-I002`），

- **发现的协议缺口（本 PR 只报告、不改 `docs/PROTOCOL.md`）**：

  5. §9 只给了 `LB-I001` 一个示例，`LB-I002`…`LB-I004` 由本实现按 `LB-I0xx` 区间自增；

## D-018 LB-007 模拟执行：立即执行、虚拟时钟 10 ms/tick、limits 判定顺序、中断与 `LB-R0xx` 码表

- **背景**：Issue #18 要求「`Ir` → `ExecEvent[]` + `ExecResult`，虚拟时钟，步数/超时限制，中断」，输出
  符合 `docs/PROTOCOL.md` §7。但 §7 只给了两份文档的形状、三句约定（`phase` / `backend` 枚举、`seq`
  严格递增、`status` 枚举）和一个示例：**没有**说一步占多少虚拟时间、`tick` ↔ 毫秒怎么换算、
  `limits` 的判定顺序与边界（恰好用满算不算超）、超时是墙钟还是虚拟时钟、`detail` 里该放什么、
  中断怎么表达（§7.2 只有 `aborted` 这个状态，没有触发方式），`§9` 的 `LB-R0xx` 也只举了
  `LB-R002`（步数上限）与 `LB-R003`（超时）两个例子。Q5（语义模型）也仍未定。
- **决策**（人类可读的定义见 `docs/EXEC.md`，机器可读的同一份在
  `src/liveblocks/runtime/semantics.py` 与 `src/liveblocks/runtime/protocol.py`；
  `tests/test_exec_docs.py` 与 `liveblocks exec report` 逐项核对两者一致）：
  1. **P0 是立即执行**（Q5 的一半答案）：一步做完就写事件，不做求值图、不做并行、不做回溯。
     `Ir` 是扁平步骤序列（D-016 第 1 条：P0 文法只有语句序列），因此「死循环」在 P0 里没有语法形态，
     只有两种**等价运行形态**：步骤数超过 `max_steps`、虚拟耗时超过 `timeout_ms`。两者都由 `limits`
     兜住，**不会挂死**；夹具 `non-terminating-steps` / `non-terminating-wait` 就是这两条，实测各
     0.1 ms / 0.04 ms 结束。
  2. **虚拟时钟 10 ms/tick**：`at_ms = Σ(cost_ticks) × 10`，不睡真实时间、不读墙钟。所有 `at_ms`
     都是 10 的整数倍（浮点可精确表示），因此事件流可以逐字节比对。`wait 100000` 只是把时钟往前拨
     1 000 000 虚拟毫秒，真实耗时仍是毫秒级——这是「死循环样例不挂死」与「测试总耗时在上限内」两条
     验收的技术依据。
  3. **op 语义表取最小可解释值**（`docs/EXEC.md` §2.3）：移动 2 tick、转向/跳跃/拿放各 1 tick、
     `wait` = 它自己写的 `duration`。世界状态是**最小网格模型**（`pos` / `facing` / `holding` /
     `jumps`），只为让 `finish` 事件的 `state_delta` 与最终状态 JSON 有内容；它**不是**产品语义，
     Q5 定稿后可能整体改写（改它必须提升 `exec_version` 并重生成 golden）。
  4. **`limits` 只读 IR**：`max_steps` / `timeout_ms` 从 `Ir.program.limits` 取（LB-006 已让它们显式
     出现，缺省 1000 / 5000），本层不设第二个上限。判定顺序固定为 **中断 → 步数 → 语义 → 超时**，
     四条都在**执行某一步之前**发生，因此被拒绝的那一步不会产出 `start`/`finish`、也不改世界状态。
  5. **边界口径**：`steps_executed` 达到 `max_steps` 且**还有步骤**没跑 → `limit_exceeded`；恰好跑完
     `max_steps` 步且程序结束 → `ok`。下一步的虚拟耗时会让总耗时**超过** `timeout_ms` → `timeout`；
     总耗时**恰好等于** `timeout_ms` 且程序结束 → `ok`（夹具 `timeout-exact` 钉住这条边界）。
     超时的虚拟时钟停在 `timeout_ms`（`duration_ms == timeout_ms`）。
  6. **事件模型**：一次运行固定为「起步 `log` → 每步 `start` + `finish`（或被一条 `error` 截断）」，
     因此 `n` 步成功运行有 `1 + 2n` 条事件。`seq` 从 1 开始严格递增，`at_ms` 单调不减。起步 `log`
     事件把 `limits` / 步数 / 时钟换算写进事件流，使「限制来自 IR」在输出里是**可见事实**。
     `detail` 按 `phase` 各有固定字段（`docs/EXEC.md` §3）。`step_id` 用空字符串表示「不绑定具体
     步骤」（目前只有起步 `log` 事件这样写）。
  7. **中断（`aborted`）**：两条入口，都只在**步骤边界**生效（不打断半步、不留半个 `state_delta`）：
     `SimExecutor.request_abort()`（`threading.Event`，可跨线程）与 `should_abort(step_index,
     elapsed_ms)` 回调（CLI 的 `--abort-at-step` / `--abort-at-ms`）。回调里调用 `request_abort()`
     也在**同一边界**生效（不必等下一步）。中断后 `status=aborted`、一条 `LB-R004`（severity `info`）。
  8. **`LB-R0xx` 码表**：`LB-R001` op 没有执行语义（防御路径：`Ir` 已按 D-017 校验，正常链路走不到，
     但下游不该崩或挂死）、`LB-R002` 步数上限（沿用 §9 示例）、`LB-R003` 超时（沿用 §9 示例）、
     `LB-R004` 被中断、`LB-R005` 手上没有物品还 `drop`（P0 网格模型的语义检查）。一次运行**最多一条**
     诊断（第一次触发就结束，不做级联）；`ok` 没有诊断。诊断只放 `LB-R0xx`，**不复制**上游
     `LB-I0xx` / `LB-P0xx`（各层诊断留在各层对象里）。
  9. **新增 `ExecState`（最终状态 JSON）**：§7 没有「最终状态」对象，而验收要求「带一个可读的状态
     输出」。本层加法式新增 `kind: ExecState`：`status` + `world`（`pos`/`facing`/`holding`/`jumps`）
     + 回显的 `limits` + `events` / `last_seq` + `exec_version`。它是**新 `kind`**，协议是否收录由
     仓库所有者决定（见下面缺口 4）。
  10. **`ExecEvent` / `ExecResult` 严格照 §7.1 / §7.2**：不加字段，`status` 与 `phase` 的枚举原样，
     §0 的「未知枚举值降级 `unknown`」在校验器里体现为额外接受 `unknown`。**`backend` 一律 `sim`**：
     `validate_run()` 里写死「出现非 `sim` 事件即实现缺陷」，从代码层面杜绝「模拟冒充硬件」。
  11. **确定性**：同一 `Ir` + 同一 `run_id` + 同一中断条件跑两次，事件流（JSONL）与最终状态（JSON）
     逐字节一致；实测墙钟耗时（`SimRun.wall_ms`）只进报告，**不进**任何文档。序列化只走
     `canonical_text()` / `events_jsonl()`。
- **影响**：
  - 执行层只吃 §6 的字段（`program.steps` + `program.limits`），因此夹具可以直接用 LB-006 的 golden
    `Ir`（`fixtures/exec` 里 3 个夹具就是上游 golden），另 5 个是手写 `Ir`（现有 golden 凑不出
    「步数用尽」「超时」「空手 `drop`」「中断」这些**执行期**形态）。
  - 虚拟时钟意味着**「耗时」与真实时间脱钩**：`duration_ms` 是虚拟的，不能当性能数据；真实性能只有
    `SimRun.wall_ms`（只进报告）。这一点必须写清楚，否则容易被读成「执行很快 = 真机也很快」。
  - 因为世界状态是 P0 占位语义，`drop` 撞上空手会**报错而不是静默忽略**：`fixtures/exec/drop-empty`
    就是如实结果。等 Q5 定稿后再决定这条检查是否保留。
- **发现的协议缺口（本 PR 只报告、不改 `docs/PROTOCOL.md`）**：
  1. §7 没说一步占多少虚拟时间，也没说 `tick` ↔ 毫秒的换算；本实现定为 10 ms/tick；
  2. §7 没说 `limits` 的判定顺序、边界（恰好用完算不算超），也没说超时是墙钟还是虚拟时钟；
  3. §7.2 的 `parse_error` 对执行器没有意义（输入已是 `Ir`），本层永不产出；建议协议注明
     「`parse_error` 由上游生产者使用」；
  4. §7 没有「最终状态」对象；本层新增 `ExecState`（新 `kind`），是否并入协议待定；
  5. §7.1 的 `step_id` 没给「不绑定步骤」的写法；本层用空字符串表示（只有起步 `log` 事件）；
  6. §9 只给了 `LB-R002` / `LB-R003`，`LB-R001` / `LB-R004` / `LB-R005` 由本实现按区间自增；
  7. §7 没说 `detail` 里该放什么；本层按 `phase` 各给一组固定字段，建议并入协议；
  8. §7 没说中断怎么触发、事件流里怎么留痕（只有 `status=aborted`）；本层用 `LB-R004` + `error`
     事件补上。
- **待办**：协议冻结前把上面 8 条并进 §7/§9（由仓库所有者决定取舍）；Q5（语义模型）定稿后重审
  §2.3 的语义表与 `drop` 的语义检查——若要改成求值图或加控制流，必须提升 `exec_version`（并连带
  `ir_version`）并重生成 `fixtures/exec` 的 golden。

## D-019 LB-008 调试视图：只读消费 §8 运行记录、一屏五层、`timings_ms`、`LB-U0xx` 与截图证据

- **背景**：LB-008 要把「帧叠加、排列、AST、IR、事件流与分层耗时」放在一屏，并支持从运行记录
  回放与单步。但 `docs/PROTOCOL.md` §8 只规定了「首行 `RunHeader`，随后按产出顺序写各层对象与事件」：
  没有 `RunHeader` 的必填字段、没有输入帧引用的字段名与解析规则、没有**分层耗时**的槽位、没有
  「一层缺了/一行坏了解析器该怎么表现」的定义，§9 也没有界面（S7b）的码区间。同时仓库坚持
  **零运行时依赖**，而「截图证据」这种产出一旦依赖第三方绘图/浏览器库，可复现性就没了。
- **决策**：
  1. **只读消费**：视图不重跑识别/排列/语法/规范化/执行，只把记录里已有的层按回放位置呈现。
     好处是「看到的现象」与「落盘的证据」是同一份数据；代价是记录里没有的层不会被补出来。
  2. **一份数据模型、三种产物**：自包含 HTML（内联 CSS + 以 base64 内嵌叠加 PNG，没有 `<script>`、
     没有外链、没有时间戳）、等宽文本（终端/CI）、叠加 PNG（仓库自带编码器）。三者同源，
     因此确定性只需证一次。
  3. **帧叠加自己画**：标记框用整数 Bresenham，文字用入库点阵字体（`data/bitmap_font.json`），
     PNG 走 `synth.png`。零依赖、字节可复现；代价是标签只有 ASCII（中文只出现在 HTML/文本形态）。
     叠加图的 PNG 压缩级别取 3（同一张 640×480 从 ~60 ms 降到 ~13 ms，体积 +2%，字节仍可复现）。
  4. **分层耗时放 `RunHeader.timings_ms`**（加法式字段），键固定为 `vision` / `layout` / `parser` /
     `ir` / `exec`；界面只**回显**记录时的实测墙钟毫秒，**不是**本屏渲染耗时，也不是性能结论。
  5. **回放 = 事件折叠**：第 0 帧是「还没处理任何事件」，第 k 帧是「处理完前 k 条 `ExecEvent`」；
     世界状态按 `detail.state_delta` 依次折叠（`pos.x/y`、`facing`、`holding`、`jumps` 后者覆盖前者，
     不插值不推断）；`finish` 缺增量时在面板上标注「世界状态不完整」。`--step N` 越界夹紧。
  6. **坏记录只报 `LB-U0xx`、绝不抛异常**：新增 9 个码（`LB-U001` 坏行 / `LB-U002` 未知 `kind` /
     `LB-U003` 缺字段 / `LB-U004` 缺层 / `LB-U005` 乱序或重复 / `LB-U006` 无 `RunHeader` /
     `LB-U007` 帧图像读不出 / `LB-U008` 事件不单调 / `LB-U009` 耗时缺失），形状沿用 §9 的诊断对象，
     另带记录行号与所属面板；层重复只保留第一份，坏行整行丢弃、其余照常。
  7. **截图证据真渲染**：`scripts/screenshot_view.py` 先用 `liveblocks.ui.render` 生成 HTML，再交给

     层次数、对比度），**不**做像素级比对（那需要固定引擎版本，本阶段不做）。
  8. **样例记录由脚本真跑各层拼出来**：`scripts/build_run_records.py` 逐层计时后写记录；
     运行记录的**生产**（`RunHeader` 打包、全链路一条命令落盘）仍属 LB-009，本层不越界。
  9. **golden = 渲染产物 sha256**：`fixtures/runs/index.json` 记录每份记录的 HTML（末帧 / 第 0 帧）、
     文本与叠加 PNG 的哈希；改视图模板或文案就必须重新生成并在 PR 里说明 diff。
- **影响**：
  - P0 场景集里只有 `clipped` 能构成可执行程序（1 步 / 3 条事件），所以「多步回放」用一份
    **只有执行层**的局部记录（`sample-all-ops`：8 步 / 17 条事件）演示；它同时是「缺层提示」的

  - 视图的确定性只覆盖「记录 → 渲染」这一段，不覆盖「记录本身」：`timings_ms` 是实测耗时，

## D-020 LB-009 端到端回归：一条命令六阶段、§8 记录由包内生产、指纹式黄金基准与 `LB-E0xx` 码表

- **背景**：
  - LB-008 为了让调试视图有真输入，写了一个拼记录的脚本（`scripts/build_run_records.py`），
    但它只为**夹具**服务：`fixtures/runs/` 是「视图的输入样例」，不是「一次运行的生产」；
    `docs/PROGRESS.md` 明确记着「运行记录的生产仍属 LB-009」。
  - `docs/PROTOCOL.md` §8 只说「首行 `RunHeader`，随后按产出顺序写各层对象与事件」，
    没有定义必填字段、没有「生成层」（LB-002 的合成卡片图像）的位置、没有记录不合格的错误模型。
  - LB-009 的验收里有一条是「回归在固定时间内完成」——需要一个**写死的上界**，而不是「感觉还挺快」。
- **决策**：
  1. 六阶段固定为 `synth → vision → layout → parser → ir → exec`，一次 `run_chain` 就是全部内容；
     生成层**真生成到磁盘**（PNG + 真值 JSON），识别从磁盘读那张图，因此记录里的
     `frame.image_ref` 指得到真文件，LB-008 的视图不需要任何额外配置就能画出叠加图。
  2. **生成层不新增 `kind`**：它的证据放在 `RunHeader.frame` + 加法式的 `generation` 块 +
     `timings_ms.synth` 里。这样记录不引入陌生行类型，LB-008 的消费侧一行都不用改（否则会报
     `LB-U002`）。记录的层 `kind` 顺序与 LB-008 的期望完全一致，跨层兼容性用真实产物证明。
  3. **记录的生产在包内**（`src/liveblocks/e2e/`），不依赖 `scripts/build_run_records.py`；
     后者继续只为 `fixtures/runs/` 的夹具服务（本单不改它）。
  4. 黄金基准 `fixtures/e2e/baseline.json` 只记**跨机器可比**的量：每层文档的
     `sha256(canonical JSON)` 指纹、`kind` 序列、行数、关键计数、生成图像/真值 sha256 与时间上界；
     **不记**墙钟耗时。基准因此是确定性的：重跑 `--update-baseline` 应得到逐字节相同的文件。
  5. 时间上界写死为整份回归 60 s、单条记录 20 s（`TIME_BOUND_MS` / `RECORD_BOUND_MS`），
     超了报 `LB-E011` 并判失败；实测值只作证据，不作性能结论。
  6. 失败定位规则：把问题按链路顺序排序，**最早一层**就是根因层——破坏注入发生在那一层，
     下游差异都是它的后果。回归默认自己做一次「破坏图像」自检，并要求它**必须**失败且点名到层；
     抓不到就报 `LB-E012`（回归是假通过）。
  7. `--corrupt` 只用于自检与手工复现，注入方式确定性（抹平图像 / 删该层一个必填字段），
     不是产品功能。
- **影响**：
  - 记录不入库（`runs/e2e` 在 `.gitignore` 里）：`timings_ms` 每次运行都不同，入库会让
    「重跑一致」变成假命题；入库的是**基准**与**记录形状的约定**。
  - 每次回归约 9–11 秒（瓶颈是生成层的纯 Python 光栅化），远低于 60 s 上界；CI 仍是
    `bash scripts/check.sh` 一条命令，没有新增流水线配置。
  - 生成层复现了 LB-002 的入库 fixture（6/6 逐字节相同），所以「整条链路的起点」不是新造的数据。
  - `--no-self-check` 会让「人为破坏一个夹具时回归明确失败并指出层级」这条验收显示未通过、
    退出码 1（默认不需要这个开关），这是刻意的：少一条证据就不算全过。
- **发现的协议缺口（本 PR 只报告、不改 `docs/PROTOCOL.md`）**：
  1. §8 没有定义 `RunHeader` 的必填字段与本层新增的 `generation` 块；
  2. §8/§1 没有「生成层」的位置：`synth` 的产物（PNG + 真值 JSON）不是协议对象；
  3. §8 没有分层耗时容器（`timings_ms` 是 U 与本层共用的加法式字段）；
  4. §8 没有「记录不合格」的错误模型；本实现新增 `LB-E0xx` 区间，未进 §9；
  5. §8 没规定记录里要不要时间戳；本实现**不写**时间戳，只有实测耗时；
  6. §8 没规定图像路径相对谁解析（本实现相对记录文件所在目录）；
  7. §8 没规定「一次运行多个场景」怎么落盘；本实现一场景一文件 `<out>/<场景名>.jsonl`；
  8. §9 没有端到端回归层的码区间与「失败摘要」格式。
- **待办**：协议冻结前把上面 8 条并进 §8/§9（由仓库所有者决定取舍）；若将来给生成层定义
  `kind`，§1 的 `Frame` 与 §8 的行序要一起改，并同步 `src/liveblocks/ui/protocol.py` 的
  `KIND_RANK` 与本层的 `STAGE_KINDS`。

## D-021 LB-030 采集台：零依赖 WSGI + 内联页面、裸灰度请求体、`LiveCaptureScene` 真值、`refused` 归档

- **背景**：LB-030 要给「真实帧」开一条入口：浏览器 `getUserMedia` 选任意摄像头、单帧/连续取帧、
  `POST /api/frame` 返回 §3 候选与叠加图、`POST /api/capture` 落盘人工标注、页面能标「识别错了」。
  约束：**优先零新增依赖**、**不改 `PROTOCOL.md`**、采集目录必须能被 `recognize report` 直接消费。
- **决策**（逐条都可回退）：
  1. **HTTP 用标准库 `wsgiref`（线程化）**，不用 FastAPI/Flask：本地单用户服务，零依赖是硬约束；
     WSGI 的调用形状（`app(environ, start_response)`）让测试可以在进程内驱动（`serve_cam.testing.TestClient`），
     不起端口、不用第三方 TestClient。代价：没有路由框架、没有中间件，全部手写（路由表在本模块与
     `docs/CAPTURE.md` 双份，文档缺口由测试反证）。
  2. **页面是单文件内联 HTML**（CSS/JS 全内联，无 `<link>`、无 CDN、无第三方脚本）：断网可加载，
     也是「验收③」唯一能机器核对的形态；导出的文件（`serve-cam page`）与服务返回的字节完全相同。
  3. **三种请求体，但页面只走裸灰度**：`image/png`（8bit 灰度，测试与命令行用来与 `recognize detect`
     逐字段对照）、`application/x-liveblocks-gray`（裸灰度 + `width`/`height`，页面用：浏览器做灰度
     转换不需要 PNG 编码库，服务端也不需要解码彩图）、`application/json`（base64，方便 curl）。
     不做彩色 PNG 解码：`synth.png.decode_gray` 只支持 8bit 灰度，扩展它会让 LB-002 的「字节可复现」
     契约变宽——不在本单范围内（D-012 仍是边界）。
  4. **帧令牌**：`/api/frame` 把最近 16 帧留在内存里并返回 `frame_token`，`/api/capture` 凭令牌取回
     **同一帧**，不必二次上传，也保证「落盘的就是刚才识别的那一帧」。令牌是内存态：进程重启即失效
     （`LB-C007`），落盘产物不受影响。
  5. **实拍真值用 `LiveCaptureScene`**，不冒充 `SyntheticCardScene`：两者字段同构（`image.file` /
     `card_layout` / `cards[].marker_id` / `marker_corners_px` / `center_px` / `status`），所以
     `vision.stats.evaluate_directory` 只要多认一个 `kind`（新增 `SCENE_KINDS`），同一份统计、
     同一套验收对照直接吃实拍样本。用同一个 `kind` 会让「合成」与「实拍」在文件名与报表里分不清。
  6. **不猜坐标**：只有拿到四角（检出角点或人工填写）的卡才写进 `scene.json`；四角拿不到的卡留在
     `capture.json` 的 `rejected_annotations` 里并给警告（`report_usable=false`）。理由：凭空坐标会
     污染 `recognize report` 的角点/中心误差。唯一的例外是**唯一标注 + 唯一检出标记**时借用该标记
     四边形，并记 `corner_source=detected-single-marker` + 警告。
  7. **不拿检测结论冒充真值**：`status` 缺省 `ok` 且写 `status_assumed=true`；`center_px` 由
     「标记四边形 + 卡面版式」外推，写 `center_source`。因此实拍样本的「卡片中心误差」只说明几何自洽，
     不是拍摄精度（写进 `docs/CAPTURE.md` §8，不许当准确率引用）。
  8. **`refused` 单独归档**：页面的「这帧识别错了」→ `outcome=misrecognised` → 落 `fixtures/live/refused/<时间戳>/`，
     目录结构与正常样本完全相同，命令只差路径；这样正常样本的统计不会被坏样本稀释，坏样本仍可单独回归。
  9. **`fixtures/live/` 不入库**（`.gitignore` 只放过 README）：实拍样本一采就变、没有「同种子重生成」，
     入库等于把仓库变成相册。
- **影响**：
  - 新增模块 `src/liveblocks/serve_cam/`（协议常量、帧输入、叠加图、采集仓库、WSGI 应用、页面、服务器、
    TestClient、文档核对），CLI 多一个 `serve-cam` 组；**唯一改动的上游文件是 `vision/stats.py` 的
    `SCENE_KINDS`**（加法式，合成场景行为不变）。
  - `bash scripts/check.sh` 仍是唯一检查入口，测试新增 6 个文件（见 `docs/PROGRESS.md`）。
  - 服务默认只绑 `127.0.0.1`；`--host 0.0.0.0` 会暴露到局域网，**本服务不做鉴权**（「不做」的一条），
    手机上的 `getUserMedia` 还需要 HTTPS 或 localhost——这两件事都留给运维侧隧道。
- **发现的协议缺口（本 PR 只报告、不改 `docs/PROTOCOL.md`）**：见 `docs/CAPTURE.md` §9 —— `Frame`
  没有设备标识与原始分辨率、§3 没有采集元数据位置、§9 没有采集侧码区间、§3 没有角点来源的表达、
  没有定义「实拍场景真值」对象。
- **发现的实现缺陷（不在本单修，先记录）**：`vision.stats._evaluate_result` 的「误检（extra）」在结构上
  恒为 0（`identified_markers` 只在遍历真值卡片时填充，所以永远不会出现「真值里没有的 marker」）。
  本单不改 LB-003 的统计口径（改了会动 LB-003 的报表与测试），但因此**不能拿「误检 0」当识别可靠的证据**；
  LB-030 的 refused 样本只用「漏检 + 识别数 + 状态」来说明问题。
- **待办**：① 协议冻结前把上面 5 条缺口并进 §2/§3/§9；② 若将来要支持彩色/JPEG 帧，需要先定义
  「帧的来源与色彩格式」再扩展 `decode_gray`；③ `extra` 统计缺陷需要单独开单修（会把 LB-003 的报表
  `误检` 列从恒 0 变成真实计数，属行为变更）。
